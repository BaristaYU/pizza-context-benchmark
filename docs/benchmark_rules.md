# 평가 규칙과 Task별 설계

구현 완료 범위와 다음 작업은 [구현 현황과 인수인계](project_status.md), 새 제작 환경의 채점은 [실행 채점](execution_scoring.md)을 따릅니다.

현재 구현된 평가는 영어 100문항의 E2E 주문 실행, 참조 계획을 주는 Tool Use, 참조 주문서를 주는 독립 Reasoning입니다. 독립 NLU와 Planning의 평가 연결은 후속 작업입니다.

## 평가 단위와 공통 규칙

평가 문항은 고객 주문 Q, 초기 환경 상태 S₀와 정답 L·A·T로 구성합니다. S는 재고와 피자 제작 단계 등 환경의 상태입니다. L은 Q의 문장 의미, A는 최종 제작 요구조건, T는 행동 계획, E는 실제 실행 기록과 최종 환경 상태입니다. “네?”는 추가 설명을 공개하는 선택 행동입니다.

NLU는 L을, Reasoning은 A를 비교합니다. Planning은 S₀의 복사본에서 후보 T를 실행해 실행 가능성과 A 충족을 검사합니다. Tool Use는 제공한 T의 수행 여부와 최종 결과를 각각 평가합니다. E2E는 실제 E의 최종 피자가 A를 만족하고 제출까지 완료됐는지 검사합니다. Q와 원문 레시피를 함께 검수해 A를 작성하고, 채점 시 새로운 조건을 추론해 추가하지 않습니다.

- 토핑 종류가 지정되면 목록은 정확히 일치해야 합니다.
- 요구된 토핑의 수량이 미지정이면 종류별 1개 이상을 허용합니다. A에 정확한 수량이나 총수량 조건이 있을 경우 그에 따릅니다. 별도 최대값은 두지 않습니다.
- 소스 `any`는 소스가 있어야 한다는 조건입니다. A의 소스 조건 생략은 사용 여부까지 자유라는 뜻입니다.
- 소스·치즈·토핑의 적용 영역은 각각 다룹니다. 토핑은 종류별로 기록하며 지정된 위치만 채점합니다.
- 조각별 균등 분포는 필수 조건으로 두지 않습니다. 같은 요구 영역·총수량에서 3·3·3과 5·3·1을 구분하지 않습니다.
- 방향 없는 반반은 전체 좌우 교환을 허용합니다. 명시된 방향은 지켜야 하며, 소스·치즈·토핑을 서로 다른 방향으로 독립 교환하지 않습니다.
- 순서 없는 여러 피자는 일대일 대응으로 비교합니다. 하나의 결과 피자를 여러 정답 피자에 재사용하지 않습니다.
- 여러 완성 주문이 정답이면 A에 완전한 대안을 보존합니다. 서로 다른 대안의 조건을 섞어 정답을 만들지 않습니다.

기본값과 재료별 규칙은 [피자 규칙](pizza_domain_rules.md)에 있습니다.

## 독립 평가와 E2E

독립 평가에는 앞 Task의 정답 입력을 제공해 이전 오류의 영향을 줄입니다. NLU는 Q에서 시작합니다. E2E에는 모델에게 중간 정답을 제공하지 않고 모델의 결과를 다음 Task로 연결합니다. 평가자는 두 경우 모두 해당 정답을 이용해 채점합니다.

| Task | 입력의 역할 | 모델 결과 | 설계할 평가 기준 |
| --- | --- | --- | --- |
| NLU | Q와 공개된 재확인 문장 | L | 의미 분석 정확도, 조건별 precision·recall·F1 |
| Reasoning | 재확인까지 반영한 참조 L, 공통 메뉴 | A | 형식 검사와 제작 요구조건 비교 |
| Planning | 정답 A, 초기 S₀, 도구 명세 | T | 계획 성공률: 실행 가능성, A 충족과 제출 |
| Tool Use / Computer Use | 검증된 참조 T, 초기 S₀, 실행 인터페이스 | 실제 호출·조작과 E | 계획 실행 성공률, 최종 결과와 제출 |
| E2E | Q, 초기 S₀, 공통 규칙과 실행 인터페이스 | L·A·T와 실제 E | 전체 주문 성공률 |

L과 A는 별도로 유지하고 파일럿에서 경계의 유용성을 확인합니다. L은 제작 추론에 필요한 언어적 근거, A는 게임 규칙과 계산을 적용한 최종 제작 요구조건입니다. 명시 조건은 두 결과에 겹칠 수 있습니다. L은 모든 문항이 함께 쓰는 객관식 주문서이며 형식과 채점은 [L 주문서 형식](linguistics_form.md)에 있습니다. 영어 100문항의 L은 팀원 작성 결과와 비교하기 전의 초안입니다. L과 A의 경계는 [L/A 설계](linguistics_answer_design.md)에 정리합니다.

구조화된 도구 API와 직접 조작하는 모의 게임은 구현돼 있습니다. 모델 실행기와 Task별 평가를 연결할 때 초기 재료, 환경 기능, 시간·행동 예산과 추가 설명 가능 여부를 기록합니다. 기존 시뮬레이터는 T의 재생·검수에, 새 모의 게임은 클릭·드래그와 좌표 기반 도구 실행에 사용합니다. 두 환경의 State와 T 형식은 [모의 게임 안내](mock_game.md)을 참고합니다.

## 추가 설명

“네?”를 선택할 때만 준비된 추가 설명을 공개합니다. 원문 주문과 추가 설명을 처음부터 합쳐 입력하지 않습니다. 원문만으로 해석 가능한지, 확인이 필요한지, 확인 후에도 미해결 조건이 있는지 검수합니다.

A에 없는 자유 속성이나 기준 기본값을 선택하기 위해 반드시 확인하도록 요구하지 않습니다. 확인 후에 확정되는 조건은 정답 A에 반영하고, 확인 판단·횟수·비용의 세부 채점은 Task별 계약에서 정합니다.

## 정답 저장 형식과 모델 응답 형식

정답 데이터의 스키마는 평가 프로그램이 정보를 저장하고 읽기 위한 약속입니다. 모델이 답변할 때 사용할 형식은 Task의 응답 규약으로 별도로 정합니다. L은 작성 도구로 팀원이 작성한 결과와 초안을 비교해 확정합니다.

모델의 응답 형식, 허용할 정규화, 형식 실패의 집계 방식은 실험 전에 고정하고 모든 모델에 동일하게 적용합니다. 이 규칙을 바꾸면 평가 버전을 구분합니다.

NLU와 Reasoning에서는 내용의 정확도와 출력 형식 준수를 구분합니다. 목록 순서, 공백, 사전에 허용한 같은 뜻의 표기처럼 의미가 변하지 않는 차이는 공통 규칙으로 정규화합니다. 원응답과 정규화 결과를 보존하고, 모델마다 다른 보정이나 누락된 답의 추론을 하지 않습니다.

내용을 확정해서 읽을 수 없는 출력은 형식 실패로 기록합니다. 이를 내용 오답으로 단정하거나 전체 평가에서 제외하지 않고, 형식 실패율을 보고하며 전체 성공률의 분모에 포함합니다. 읽을 수 있는 답의 의미 정확도를 함께 제시할 경우에는 그 대상 수를 명시합니다.

응답 규약을 지킨 답을 파서가 읽지 못하면 파서를 수정하고 같은 기준으로 재채점합니다. 올바른 주문을 정답 스키마가 표현하지 못하면 스키마와 채점 기준을 보완합니다. 원문·정답·채점기 문제를 모델의 의미 이해 오류로 처리하지 않습니다. 구현된 A 응답 규약과 판정 기록은 [독립 Reasoning 평가](model_runs.md#독립-reasoning-평가)에 있습니다.

## 병목 분석

독립 평가와 E2E를 같은 주문에서 비교해 병목 후보를 찾습니다. 보완 실험은 선택한 Task의 모델 출력만 정답으로 교체하고 나머지 조건을 유지합니다. 여러 앞 단계를 함께 건너뛴 결과는 해당 Task만의 효과로 해석하지 않습니다. 기본 E2E와 정답 대체 실험의 결과는 구분해 보고합니다.

## 실행과 재현성

E는 실행 환경이 생성합니다. 참조 E도 참조 T를 실행해서 만듭니다. E의 trace는 행동별 성공·오류 기록이며 final_state는 실행이 끝난 환경 상태입니다. 문항에는 Q·S·L·A·T와 참조 E를 함께 저장하고, 모델의 실제 실행 레코드는 case_id로 연결해 보관합니다. 실행 결과의 A 충족과 제출 완료를 검사합니다. 원본 게임과 연결할 때는 게임 만족도도 별도로 관측합니다.

모델, 프롬프트, 데이터·Registry·환경 버전, 초기 설정, 행동·시간 예산, 난수 seed, 반복 횟수, 원본 응답과 행동 로그를 저장합니다. 형식 오류·실행 실패·시간 초과도 결과에 남깁니다. 주 지표와 세부 오류의 집계 방식은 Task별 계약에서 확정합니다.

## 참고한 평가 설계

[τ-bench](https://arxiv.org/abs/2406.12045)는 도구를 실행한 후 결과 상태를 이용해 목표 달성을 평가합니다. [τ²-bench](https://arxiv.org/abs/2506.07982)는 통제된 조건과 보완 실험으로 능력 차이를 분석합니다. [OSWorld](https://arxiv.org/abs/2404.07972)와 [OSWorld 2.0](https://arxiv.org/abs/2606.29537)은 실제 컴퓨터 환경의 작업을 다룹니다. 본 프로젝트는 이를 참고해 동일한 주문·초기 환경에서 해석·계획·실행의 차이를 분석하는 설계를 검토합니다.

현재 도구의 선행 조건과 실행 방법은 [모의 게임 안내](mock_game.md)에 있습니다. Planning은 유효한 다른 행동 순서도 허용합니다. Tool Use는 제공한 계획의 대상·인자·순서를 실제 실행과 대조합니다. 최종 피자가 A를 만족하는지와 계획을 수행했는지는 각각 보고합니다. API 요청 구성, 응답의 대상 ID 연결, 관측, 오류 대응을 포함한 실행 평가는 [모델 실행](model_runs.md)에 있습니다.
